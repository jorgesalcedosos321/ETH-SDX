Payment · Lifecycle

Transaction lifecycle

Explicit async state machine for Ethiopian wallet and bank rails — statuses and operational FAQs as implemented in production.

Async-firstProduction API
Why this matters: Telebirr, CBE, M-Pesa, and similar rails are asynchronous. An HTTP 200 on transfer often means “accepted / popup sent,” not “paid.” Final state arrives on your notifyUrl and via verify APIs. See also Recommended merchant pattern and Webhook shape.

State machine

Map the product flow to TransactionStatus and session outcomes.

Session created

POST /api/checkout/session succeeds. You get sessionId + paymentUrl. No paid transaction yet — treat this as the start of the lifecycle (there is no CREATED enum; the session exists and is awaiting payment).

PENDING

Payment started (USSD popup, OTP, card redirect, etc.). Status stays PENDING on the session transaction until the rail finishes.

SUCCESS

Wallet/bank/card confirmed. Merchant notifyUrl receives a webhook with transactionStatus SUCCESS. Treat SUCCESS as paid.

FAILED

Customer declined, wrong PIN, insufficient funds, or provider failure. Webhook carries FAILED when the rail reports failure.

EXPIRED

expireDate passed while still unpaid/pending. The gateway marks the transaction EXPIRED.

CANCELLED

Merchant cancels a pending session (e.g. POST cancel). The transaction status becomes CANCELLED.

Transaction statuses: PENDING, SUCCESS, FAILED, CANCELLED, EXPIRED, UNAUTHORIZED, FORBIDDEN. A successful session may also show session status COMPLETED — that is not a separate charge step after SUCCESS. UNAUTHORIZED / FORBIDDEN appear on auth failures, not as normal payment outcomes.

Questions developers actually ask

Operational rules for webhooks, timeouts, retries, abandoned browsers, and double charges.

Customer paid but I never got the webhook — what do I do?

Do not trust the browser redirect alone. Call verify (see Recommended merchant pattern). Source of truth is the gateway status (SUCCESS/FAILED/PENDING), not whether your notifyUrl returned 200. Delivery attempts are logged; the gateway does not auto-retry webhooks.

What if my API call times out?

A client timeout does not mean the payment failed. Keep the sessionId (and nonce). Poll or call verify until the status leaves PENDING, or wait for the webhook.

What if I retry the same create/direct call?

Reuse the same nonce → gateway returns "session already exist". Always generate a new nonce per new checkout attempt. Creating a new session with a new nonce can charge again — bind nonce/orderId in your DB.

Customer closes the browser mid-payment?

The wallet/bank flow often continues asynchronously. Rely on notifyUrl + verify APIs. Closing checkout does not cancel a PENDING Telebirr/M-Pesa/CBE attempt automatically.

Can the same order be charged twice?

Yes, if you create two sessions (two nonces) for one order. Store one sessionId per orderId and refuse a second create until the first is FAILED/EXPIRED/CANCELLED.
